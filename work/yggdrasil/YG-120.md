## As
O time que quer o handshake do bridge **sendo aceito** pelo CO-384 (não 401/403 silencioso).

## I Need
Que o dial (YG-119) mande `source` + `token` como **query params** (`?source=<node_id>&token=<token>`),
como o `bridge_ws_handler` do CO-384 lê (`Query<BridgeQuery>`) — não só no header `Authorization`.

## So That
A conexão é aceita: CO-384 confere `source` na trust-list (`CO_BRIDGE_TRUSTED_SOURCES`) + token
não-vazio. **JWKS/validação cripto NÃO é necessário** — o CO-384 mergeado não valida assinatura.

## Context
Auditoria 2026-06-09 do `co-web/src/eda/bridge/handler.rs` mergeado: `bridge_ws_handler` lê
`source`+`token` da **query**, rejeita source fora da trust-list (403) e token vazio (401), e
**não** valida o token cripto (sem JWKS). O dial YG-119 mandava o token só como Bearer header →
CO-384 veria `?token=` vazio → 401. Gap de transporte ("verde dos dois lados, zero federação").
Reescopo: o slot YG-120 (era "JWKS") vira **alinhamento de handshake**; JWKS fica fora de escopo
(o CO-384 atual não precisa).

## Acceptance
- **GIVEN** `BridgeConfig{url,token,node_id}`  **WHEN** monta a request de handshake
  **THEN** a URI é `<url>?source=<node_id>&token=<token>` (`&` se a url já tem query; valores
  percent-encoded), além do Bearer + subprotocol `co.eda.bridge.v1`. (testes de unidade)
- **GIVEN** o `node_id`  **THEN** é o host de deployment que casa `CO_BRIDGE_TRUSTED_SOURCES`
  (default `yggdrasil.artelonga.com.br`, override por `YGG_CO_BRIDGE_NODE_ID`).

## Não no escopo
- JWKS / minting de service JWT assimétrico — desnecessário com o CO-384 atual (trust-list +
  token não-vazio). Reabrir só se o CO adicionar validação de assinatura.
- Secrets/deploy + E2E ao vivo — YG-121.

## Dependencies
- YG-119 ✅ (dial). CO-384 ✅. Destrava YG-121 (E2E).
