GIVEN scenes + signals + multiplayer + JWT funcionam isolados
(YG-32..YG-34), mas nenhum universo de jogo de verdade foi feito,
WHEN construo `PokerTable.tscn` end-to-end (6 assentos, bot
fallback, buy-in/cash-out chamando Rust, gameplay com signals)
e rodo paralelo à versão canvas (YG-23/25/26/27 do trilho Rust),
THEN tenho **dados reais** para a decisão de migração: comparar
dev velocity, peso do payload, ergonomia mobile, custo de deploy.

## Por que é o último task do POC

Esta é a tarefa-decisão. Se YG-35 sair em prazo razoável e o
resultado superar a versão canvas em developer experience + UX
multiplayer, marcamos para migrar snake/tetris/invaders em YG-36+.
Se sair pior ou demorar 2x mais, mantemos o trilho canvas e
arquivamos `yggdrasil-godot/` como aprendizado.

## Critérios de aceitação

### PokerTable.tscn

- [ ] `scenes/PokerTable.tscn` com:
  - [ ] 6 instâncias de `Seat.tscn` em layout circular.
  - [ ] `Pot.tscn` central exibindo total em sementes.
  - [ ] `CommunityCards.tscn` (5 placeholders).
  - [ ] `ActionBar.tscn` (botões call/raise/fold/check, mostrado só na vez do peer local).
- [ ] `Seat.tscn`:
  - [ ] Estados visuais: Empty / Human / Bot / Self.
  - [ ] Sinais autoritativos (server-emit): `seat_taken`, `seat_freed`, `bot_appeared`, `bot_left`.
  - [ ] Sinais de intenção (client-emit RPC): `request_sit(seat: int)`, `request_stand()`.
- [ ] `PokerTableServer.gd`:
  - [ ] Espelha lógica de `yggdrasil-core::games::poker_lobby` (regras de bot).
  - [ ] `start_hand()` quando ≥ 2 ocupantes — distribui hole cards via `cards_dealt` autoritativo filtrado por peer.
  - [ ] Estado de mão (deck, pot, current_actor) — gerencia bet rounds.
  - [ ] Showdown declara vencedor por `EvaluatedHand` (port mínima de game_core ou implementar em GDScript).

### Bot

- [ ] `Bot.tscn` — subscriber de `actor_changed`, decide ação aleatória legal, emite `request_action` via RPC fake (servidor processa direto sem network).

### Sementes bridge

- [ ] Rust expõe (novo, mínimo):
  - [ ] `POST /api/v1/sementes/debit` body `{user_id, amount}` (header JWT do server, não do usuário — service-to-service).
  - [ ] `POST /api/v1/sementes/credit` body `{user_id, amount}`.
  - [ ] Header `X-Yggdrasil-Service-Token` validado com env var separada.
- [ ] Godot side: `lib/sementes_client.gd` faz HTTPRequest ao Rust.
- [ ] Buy-in debita ao sentar; cash-out credita o stack remanescente ao levantar.

### Validação E2E

- [ ] Demo gravada (3 min):
  - [ ] Dois browsers logam.
  - [ ] Browser A senta na mesa, bot aparece.
  - [ ] Browser A joga uma mão contra o bot — vê cartas, aposta, mão termina, sementes mudam.
  - [ ] Browser B senta, bot some, A e B jogam uma mão entre si.
  - [ ] Kill -9 do server no meio da segunda mão.
  - [ ] Restart → mão continua do mesmo ponto (event replay via YG-33).
- [ ] Métricas registradas em `docs/POC-METRICS.md`:
  - [ ] Peso do payload web (.wasm + .pck).
  - [ ] Tempo de cold load no Chrome desktop + Chrome mobile.
  - [ ] Linhas de código GDScript vs equivalent Rust+JS canvas (YG-23+25+26+27).
  - [ ] Tempo total das 5 tarefas YG-31..YG-35 (horas reais de trabalho).

### Decisão registrada

- [ ] `docs/ADR-002-godot-poc-resultado.md` — escrever ao final com:
  - [ ] **Resultado**: bate ou não bate canvas em cada métrica.
  - [ ] **Decisão**: migrar / não migrar / migrar parcialmente (ex.: só mobile via PWA Godot, browser desktop fica canvas).
  - [ ] **Próximas tarefas**: YG-36+ se migrar, ou arquivamento da branch se não.
