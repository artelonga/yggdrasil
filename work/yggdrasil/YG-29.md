GIVEN o `PokerState` de YG-23 é `Mutex<Vec<PokerLobby>>` em memória —
um restart do servidor (deploy, crash) zera todas as mesas e perde
buy-ins,
WHEN persisto `PokerTable` (seating + hand state) em SQLite via
`game_core::storage::Storage`,
THEN deploys são transparentes para quem está sentado, e crashes não
custam sementes.

## Critérios de aceitação

- [ ] Schema SQLite:
  - [ ] `poker_lobbies(id TEXT PRIMARY KEY, name TEXT, state JSON)`.
  - [ ] `poker_hands(lobby_id TEXT, hand_id TEXT, state JSON, started_at INTEGER, ended_at INTEGER)`.
  - [ ] Reusar `YGGDRASIL_DB` (já em volume Fly).
- [ ] `PokerState::new`:
  - [ ] No boot, carrega lobbies persistidos. Se não houver, cria os dois defaults.
  - [ ] Re-cria broadcaster (YG-28) por lobby carregado.
- [ ] `PokerTable::sit/stand/act` chamam `Storage::save_poker_lobby` após cada mutação.
- [ ] Hand histories são append-only — nunca update.
- [ ] Teste: kill -9 do processo em meio a uma mão e restart → mão continua do mesmo ponto.

## Não-objetivos

- Migração de schema (primeira versão; futura mudança será YG-31).
- Postgres (volume + LiteFS resolve para a fase 0).
