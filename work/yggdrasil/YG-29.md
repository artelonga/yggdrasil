GIVEN o `PokerState` de YG-23 é `Mutex<Vec<PokerLobby>>` em memória —
um restart do servidor (deploy, crash) zera todas as mesas e perde
buy-ins,
WHEN persisto `PokerTable` (seating + chip-stacks) em SQLite via uma
conexão `rusqlite` dedicada (mesmo `YGGDRASIL_DB`),
THEN deploys são transparentes para quem está sentado, e crashes não
custam buy-ins.

## Critérios de aceitação

- [x] Schema SQLite:
  - [x] `poker_lobbies(id TEXT PRIMARY KEY, name TEXT, state TEXT)` — `state` contém JSON com `lobby` + `stacks`.
  - [x] Reusa `YGGDRASIL_DB` (mesmo volume Fly).
- [x] `PokerState::with_persistence`:
  - [x] No boot, carrega lobbies persistidos. Se vazio, semeia 3 defaults (Mesa Carvalho, Mesa Olmo, Heads-Up Carvalho) e persiste.
  - [x] Falhas de SQLite degradam graciosamente para in-memory + warning no log.
- [x] `PokerTable::sit_with_sementes / stand_with_sementes / act` acionam `persist_table` após cada mutação bem-sucedida.
- [x] `PokerTable::to_snapshot()` / `from_snapshot()` em `yggdrasil-core` — round-trip via JSON cobre seating + stacks.
- [x] Teste: simular crash via drop + reopen do mesmo `db_path` → seats e stacks idênticos.

## Não-objetivos

- **Persistência da mão em curso (`PokerGame`)**. O engine `PokerGame` do `co/game-core` não é serde-friendly; implementar serialização exigiria modificar `co/`, o que viola a regra "estabilidade do engine". Trade-off pragmático: mãos em curso são forfeit num restart (custo máximo: o pot atual, ≤ algumas dezenas de sementes), mas buy-ins (1k+) sobrevivem. Hand histories append-only (`poker_hands`) ficam para YG-31 ou posterior.
- Broadcaster por lobby (YG-28) — não está implementado ainda, então este task não precisa re-instanciar.
- Migração de schema (primeira versão; futura mudança será YG-31).
- Postgres (volume + LiteFS resolve para a fase 0).
