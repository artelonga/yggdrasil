## As

O Yggdrasil em produção (`yggdrasil-artelonga.fly.dev`), que **hospeda** as notas
(`/data/instances/<id>/notes/<slug>.md`, Phase 0 shipped 2026-06-06) e precisa publicá-las
ao CO em tempo real, sem polling.

## I Need

Um **producer de eventos** que conecta **outbound** ao hub do CO (`wss://co.artelonga.com.br/api/v1/events/bridge`)
e emite `entry.{created,updated,deleted}` a cada escrita/remoção do `NoteStore`, autenticado por um
**service JWT emitido pelo CO** (validado pelo CO contra a própria chave — a mesma relação de confiança
JWKS já usada no handover SSO de `auth_co.rs`).

Topologia: **CO is hub.** O Yggdrasil **disca para fora**; o CO aceita a conexão inbound, valida o token,
e faz fan-out (CO-384). Este task NÃO inclui aplicar eventos vindos do CO (isso é Fase P-B, v3.1).

## So That

- **CO-383 (ingest read-only, Wave 4 Batch C) tem seu pré-requisito.** Sem este producer, o CO não recebe
  nenhuma nota e o **Tema 7 do v3.0 não fecha**. Logo este é um **gate de release** do v3.0.
- A latência cai de "nunca" (não havia transporte) para <1s (push por evento).
- O Yggdrasil-keeps-notes materializa: Yggdrasil é a fonte; o CO assina o stream.

## Context

**Dimensionamento realista — NÃO são ~50 LOC** (o CO-383 estimou por baixo). O escopo real:

1. **Hook de emissão** em `NoteStore::save`/`delete` (`yggdrasil-core/src/instance/note.rs`): publica
   `NoteWritten{instance, slug, sha, kind}` num canal `tokio::sync::broadcast` — mesmo padrão do
   poker (`yggdrasil-core/src/games/poker/events.rs`, `yggdrasil-web/src/games/poker/ws.rs`).
2. **Background task com client WS outbound** (tungstenite): mantém a conexão ao hub do CO, heartbeat 30s,
   **reconnect com backoff** (1s→2s→4s→…→30s), e **fila de replay offline** (eventos enfileirados quando o
   CO está fora; drenados no reconnect). Padrão de spawn: `universos_routes::spawn_cleanup_job` em `main.rs`.
3. **Envelope de evento** compatível com `FederatedEvent` do CO-384 (`event` + `origin_deployment` +
   `signed_by` + `hop_count`); `event_type = entry.{created,updated,deleted}`, `universe_key = yggdrasil`,
   `path = notes/<slug>.md`, `payload = {title, body, updated_at}`.
4. **Auth**: apresenta um service JWT emitido pelo CO; client HTTP/WS reusa o padrão `reqwest`/JWKS de
   `auth_co.rs` (`hint_engine.rs` para a forma do client). Refresh em expiração.
5. **Echo/loop guard**: respeita `hop_count` e não reemite eventos recebidos (no v3.0 não recebemos, mas o
   guard fica pronto para P-B).
6. **`event_log` + cold-start (mesmo code path do reconnect)**: rastreia `last_delivered_event_id` (ACK do CO).
   - `last_delivered_event_id = NULL` (primeira conexão / staging resetou) → stream do **`event_log` inteiro** =
     backfill de **todas** as notas existentes, não só futuras.
   - reconnect após offline → stream a partir do último id ACK'd. Mesmo código p/ warm-reconnect e cold-start;
     o CO deduplica por ULID (idempotente, CO-380).
   - **Nuance**: as notas da Phase 0 já em disco **não têm** entradas no `event_log` (são anteriores a ele). No
     primeiro boot o producer **semeia** o log enumerando `NoteStore::list` por instância e sintetizando um
     `entry.created` por nota; daí em diante o log é append-only por `save`/`delete`.

Reuso: `auth_co.rs` (JWKS + reqwest), poker `broadcast` (events.rs/ws.rs), `spawn_cleanup_job` (task de
background). Config nova: `YGG_CO_BRIDGE_URL`, `YGG_CO_BRIDGE_TOKEN` (via `flyctl secrets`).

## Acceptance

- **GIVEN** uma nota salva via `NoteStore::save`
  **WHEN** a escrita atômica conclui
  **THEN** um `NoteWritten` é publicado no canal `broadcast` interno (1 evento por save/delete).

- **GIVEN** `YGG_CO_BRIDGE_URL` + `YGG_CO_BRIDGE_TOKEN` configurados
  **WHEN** o servidor sobe
  **THEN** o producer disca outbound ao hub do CO e o CO aceita a conexão (source em `CO_BRIDGE_TRUSTED_SOURCES`).

- **GIVEN** o producer conectado
  **WHEN** uma nota é criada / atualizada / removida
  **THEN** o CO recebe `entry.created` / `entry.updated` / `entry.deleted` em < 1s (verificável em `/agora`).

- **GIVEN** a conexão WS cai (CO reinicia / partição de rede)
  **WHEN** o producer detecta o drop
  **THEN** reconecta com backoff exponencial e **drena a fila de eventos pendentes** sem perda nem duplicação
  (eventos idempotentes por id/ULID).

- **GIVEN** o CO sobe pela primeira vez (ou staging resetou) — sem `last_delivered_event_id`
  **WHEN** o producer conecta
  **THEN** faz stream de **todas** as notas existentes (`event_log` inteiro, incluindo as da Phase 0 semeadas no
  primeiro boot), não só as futuras; o CO as ingere idempotentemente (dedupe por ULID) — mesmo code path do reconnect.

- **GIVEN** um token inválido/expirado
  **WHEN** o producer tenta conectar
  **THEN** o CO rejeita (403); o producer faz refresh do token e re-tenta (alerta no log).

- **GIVEN** o gate de release do v3.0
  **WHEN** o E2E do CO-383 roda na Batch C
  **THEN** ele **falha** se este producer não estiver shipado — este task é pré-requisito bloqueante do Tema 7.

## Sizing (estimativa realista)

~250–350 LOC (não 50): hook broadcast ~30 · client WS + reconnect/replay ~180 · envelope+auth ~80 ·
testes de integração ~120. Novo arquivo: `yggdrasil-web/src/co_bridge_producer.rs` + 1 hook em `note.rs` +
wiring em `main.rs`.

## Dependencies

- **CO-384** (Wave 4) — o hub `/api/v1/events/bridge` precisa existir no CO e aceitar inbound do Yggdrasil
  (`CO_BRIDGE_TRUSTED_SOURCES=yggdrasil.artelonga.com.br` + service JWT emitido para o Yggdrasil).
- **CO-383** (Wave 4) — o consumer do outro lado.
- **Phase 0 NoteStore** ✓ shipado (2026-06-06) — a fonte dos eventos.

## Not in scope

- **Aplicar eventos inbound** (CO → Yggdrasil write-back) — Fase P-B, **v3.1**.
- **Conflict resolution / UPSERT** (CO-385) — **v3.1**.
- **Bidirectional** — v3.0 é producer→hub one-way (read-only no CO).
- **Hospedar um bus próprio no Yggdrasil** — descartado; "CO is hub", Yggdrasil disca para fora.
