## YG-154 — Integração — portar drag-drop+persist (YG-149) pro MundoView do instance view; salvar o backend, redoer só o front

Une os dois surfaces que o build paralelo 148/149 divergiu: o backend de persistência
de layout (YG-149) é salvo intacto e o drag-drop/reparent é reimplementado **sobre o
`MundoView`** (engine real do YG-148, instance view) — não mais na página proto standalone.

### Backend (salvo do YG-149, surface-agnóstico)
- `instance/note.rs`: `NotePos{room,x,y}` + `parent` no frontmatter `.md`; `set_pos`,
  `set_parent` e `apply_layout` (commit em lote); `save`/`save_with_status`/`set_status`
  preservam o layout (editar o corpo nunca move o objeto no Mundo).
- `api/instances.rs`: `POST /api/v1/instances/{id}/layout` (owner-only) aplica os
  movimentos em lote e federa um patch por nota; `note_frontmatter` leva `status`+layout.
- `co_bridge_producer.rs`: `NotePayload.frontmatter` carrega `pos`/`parent` no write-back ao CO.

### Frontend (reimplementado sobre o MundoView, não no proto)
- `mundo/instance-view.js`: liga `onDragDrop` da engine real — arrastar uma nota para uma
  célula livre reposiciona; soltar numa porta reparenta. Cada solta vira um movimento no
  `coordMap` em memória → commit **em lote** ao `POST /layout` → grava `.md` → write-back CO.
  Sem localStorage: o surface real é a instância e a verdade é o `.md`/CO.
- `mundo/loader.js`: `applyLayout` sobrepõe o auto-layout com `pos`/`parent` persistidos —
  reabrir o Mundo mantém para onde cada objeto foi arrastado.
- e2e Playwright **no instance view** (`window.MundoView`): arrastar → reload → posição
  mantida; reparent → nota na nova pasta após reload.

### Why
Corrige a divergência do build paralelo (engine real no `MundoView`, drag-drop órfão na
página proto). O Mundo real ganha manipulação direta durável e sincronizada com o CO num
único surface coeso, desbloqueando o YG-153 (import do CO + CRUD). Supersede o PR #81.
